# 1. Context, goals and principles

## 1.1 What we are building

The **Enterprise Knowledge Context Platform (EKC)** is a self-hosted "enterprise AI brain". It:

1. **ingests** an organisation's knowledge: documents, wikis, tickets, source code, databases and APIs;
2. **models** it as searchable content *and* as a graph of business domains, applications, services, APIs, data stores and code;
3. **answers** questions and assists engineers with permission-aware, cited answers generated by **self-hosted** models;
4. **enriches** itself from approved external sources only when internal knowledge is insufficient, and only through review;
5. **meets developers in VS Code** with chat, inline completion, refactoring and repository-aware generation.

## 1.2 Goals

| # | Goal | Measured by |
|---|---|---|
| G1 | Runs with no third-party LLM service | every core path passes with egress to external AI blocked |
| G2 | Same code from laptop to cluster | one codebase; the hardware profile is configuration only |
| G3 | Answers grounded in enterprise knowledge, with citations | citation faithfulness ≥ 0.9 on the evaluation set |
| G4 | Nobody sees knowledge they could not see in the source system | zero ACL leaks in permission test suites; checks happen at retrieval time |
| G5 | Understands flows across services, not just text | impact-analysis questions answered from the knowledge graph, with paths cited |
| G6 | Developers use it daily inside VS Code | inline completion p50 < 500 ms on the GPU profile; chat within the IDE |
| G7 | Knowledge stays fresh without manual effort | source change → searchable in < 15 min (incremental sync) |
| G8 | Fully auditable | every ingestion, enrichment, approval, query and access decision logged |

## 1.3 Non-goals (for v1)

- Training or fine-tuning foundation models. Learning happens by **indexing approved knowledge**. Fine-tuning adapters (LoRA) on approved code is a later, optional capability.
- Replacing source systems. EKC mirrors and indexes; SharePoint, Confluence, Jira and Git remain the systems of record.
- Autonomous code changes without a human. The assistant proposes diffs, and the developer applies them.
- Multi-region active-active. A single region with backup and restore comes first.

## 1.4 Principles

1. **Self-hosted first, external by exception.** Embedding, retrieval, generation and completion run on self-hosted models. External LLMs and the open web are reachable only from the Enrichment service, through an egress gateway, under policy, and their output is quarantined until approved.
2. **Internal knowledge wins.** Trust tiers are ordered: *Authoritative internal > Verified (approved) > Internal unreviewed > External quarantined*. External content can never overwrite or outrank internal content without an explicit, audited approval.
3. **Deny by default, enforce at retrieval.** Permissions are mirrored from source systems and checked *inside* the search query, then re-checked before the answer is returned. The LLM never receives text the user may not read.
4. **Model-agnostic.** All runtimes are reached over the OpenAI-compatible HTTP protocol (Ollama, vLLM, llama.cpp server) or the TEI protocol (embeddings and reranking). Each model is chosen per task and per hardware profile by configuration.
5. **Deterministic pipelines, agentic only where it pays.** Ingestion and RAG are explicit pipelines that are testable and repeatable. Agent loops with tools are used for multi-step questions such as impact analysis and code changes, with read-only tools by default.
6. **Provenance everywhere.** Every chunk, graph edge and answer sentence traces back to a source, a version and an ingestion run.
7. **Plug-and-play.** Connectors, parsers, model runtimes and vector stores are adapters behind ports, so adding one means no core changes.
8. **Boring infrastructure.** PostgreSQL is the system of record (metadata, ACLs, graph, audit). Few moving parts on a laptop; scale out only by profile.
9. **Everything as code.** Infrastructure (OpenTofu, Helm, Compose), policies (OpenFGA model), dashboards, evaluation sets and prompts are all versioned in Git.

## 1.5 Quality attributes and targets

| Attribute | Laptop profile | Server profile |
|---|---|---|
| Chat answer, time to first token | < 8 s (CPU) | < 1.5 s |
| Inline completion p50 | best effort (~1–2 s) | < 500 ms |
| Concurrent users | 1 | 50–200 per GPU node |
| Corpus | ~50k chunks | 10M+ chunks (Qdrant sharded) |
| Availability | n/a | 99.5% (single region, HA API and DB) |
| RPO / RTO | daily backup | RPO 15 min (WAL archiving), RTO 4 h |

## 1.6 Constraints and assumptions

- .NET 10 (LTS) backend, TypeScript VS Code extension, Python only where the best open-source tooling is Python (Docling, evaluation).
- Licences must permit self-hosted commercial use: Apache-2.0, MIT, MPL-2.0 or BSD for components; model licences are checked per model (see the technology stack).
- The reference development machine is a 16 GB Intel Mac with no GPU. It must run the **laptop** profile end-to-end with small models. Copilot-grade quality needs the **workstation-gpu** or **server** profile.
